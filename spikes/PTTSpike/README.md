# PTT Spike #2 — push-to-talk → paste injection

Proves the Hark headline interaction in isolation, with **no audio/STT**:

> hold **right ⌘** → "recording" → release **right ⌘** → a canned string
> (`[hark] dictated at <timestamp>`) is pasted into whatever field is focused.

SwiftPM command-line executable, Swift 6, macOS 15+.

## Build & run

```sh
cd spikes/PTTSpike
swift build
./.build/debug/ptt          # or: swift run ptt
```

Quit with **Ctrl-C** (the event tap is disabled and invalidated on the way out).

Env knob: `HARK_NO_AX_PROMPT=1` checks Accessibility trust without popping the
system permission dialog (useful for scripted/CI runs).

## Accessibility (TCC) — required

The hotkey uses an active `CGEventTap` on `flagsChanged` events, which requires
the **Accessibility** permission. Because `ptt` is a plain CLI binary, macOS
attributes the permission to the app that *launched* it — i.e. **your terminal**,
not the binary:

1. System Settings → **Privacy & Security → Accessibility**
2. Enable (or add with **+**) your terminal app — Terminal.app, iTerm2,
   VS Code, Ghostty, …
3. Quit and relaunch the terminal, then run `ptt` again.

On first run without permission, `ptt` triggers the system prompt (unless
`HARK_NO_AX_PROMPT=1`), prints the guidance above, then fails tap creation and
exits with status 1.

## What it does

1. **Hotkey** — active CGEventTap (`.cgSessionEventTap`, `.headInsertEventTap`,
   `.defaultTap`) listening only to `flagsChanged`. Right ⌘ is keycode `0x36`
   (left is `0x37`); press/release is derived from `.maskCommand` appearing /
   clearing, with state tracking so each edge fires exactly once.
   `tapDisabledByTimeout` / `tapDisabledByUserInput` are handled by immediately
   re-enabling the tap — the system disables stalled taps, and without this the
   hotkey goes permanently deaf.
2. **Hold semantics** — press prints `listening…`; release under 300 ms is
   treated as a tap and ignored (toggle mode is out of scope for this spike);
   longer holds run the paste sequence.
3. **Paste** (the VoiceInk-style field-tested recipe):
   - snapshot *all* current pasteboard items with all their types/data;
   - `clearContents()`, write the transcript plus markers
     `org.nspasteboard.TransientType` and `org.nspasteboard.AutoGeneratedType`
     (empty data, so well-behaved clipboard managers skip it) and a private
     `com.hark.session` type carrying a per-paste UUID;
   - wait 100 ms;
   - post ⌘V as four CGEvents from a `CGEventSource(stateID: .privateState)` —
     cmd↓, v↓, v↑, cmd↑ — 10 ms apart, to `.cghidEventTap`;
   - after ~300 ms more, restore the snapshot **only if** the pasteboard still
     contains our `com.hark.session` UUID (the user may have copied something
     else in the meantime).
4. **Secure input guard** — before pasting, `IsSecureEventInputEnabled()`
   (Carbon) is checked; if a password field holds secure input, the synthetic
   ⌘V is skipped, the text is left on the clipboard, and a warning is printed.

## Expected output

```
[hark] event tap live. Focus any text field and hold RIGHT ⌘ …
[hark] listening… (release right-command to paste)
[hark] held 812 ms — pasting…
[hark] pasted. release -> paste-complete: 142.3 ms
[hark] previous clipboard restored (1 item(s)).
```

…and `[hark] dictated at 14:02:33` appears in the focused field.

### Latency numbers

- **held N ms** — how long right ⌘ was down (hold duration).
- **release → paste-complete N ms** — hotkey release to the last ⌘V CGEvent
  being posted. Floor is ~130 ms by construction: 100 ms pasteboard settle +
  3 × 10 ms inter-event gaps + scheduling. This is the budget the real app pays
  *on top of* STT time; if the recipe proves reliable, the 100 ms settle is the
  first knob to shrink.
- Clipboard restore happens ~300 ms after the paste and is not on the critical
  path the user perceives.

## Known failure modes

- **Secure input** (password fields, some auth dialogs; occasionally a stuck
  grab from another app): synthetic keys won't be delivered. `ptt` detects this,
  skips the paste, leaves the text on the clipboard, and prints how to find the
  offender (`ioreg -l -w0 | grep SecureInput`).
- **Clipboard managers**: managers that ignore `org.nspasteboard.TransientType`
  will record the canned transcript in their history. Managers that *rewrite*
  the pasteboard immediately can also defeat the restore check (we then leave
  the pasteboard alone rather than clobber it).
- **Apps that don't honor ⌘V** (some games, remote-desktop windows, Electron
  apps with intercepted shortcuts): nothing is inserted; the text is still on
  the clipboard until restore kicks in ~400 ms later.
- **Both command keys held**: press/release is derived from `.maskCommand`
  presence, so releasing right ⌘ while *left* ⌘ is still held is not seen as a
  release until all command keys are up. Fine for a spike; the real app should
  key off the device-specific right-cmd flag bit (`0x10` in raw flags).
- **Tap disabled by the system**: handled (auto re-enable), but if the process
  is suspended long enough the WindowServer may drop events on the floor first.

## Status

- `swift build` succeeds — Swift 6.3.3 toolchain, macOS 26 SDK, zero warnings.
- Permission-failure path **verified**: run without Accessibility trust prints
  the TCC guidance, fails tap creation, exits with status 1 (tested with
  `HARK_NO_AX_PROMPT=1` from a non-trusted shell).
- The happy path (tap fires, paste lands, clipboard restores) **needs a human**:
  grant Accessibility to your terminal, run `./.build/debug/ptt`, focus a text
  field (TextEdit, a browser form, Slack), hold right ⌘ ~1 s, release, and
  confirm the canned string appears and the previous clipboard comes back.
  Repeat once in a password field to see the secure-input guard, and once with
  a clipboard manager running to observe restore interplay.
- Swift 6 note: the imported C global `kAXTrustedCheckOptionPrompt` is a `var`
  and trips strict concurrency from main-actor top-level code; the literal key
  string `"AXTrustedCheckOptionPrompt"` is used instead (same value).
